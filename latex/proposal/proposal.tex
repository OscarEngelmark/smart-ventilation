\subsection{1. Use case, and why}\label{use-case-and-why}

This project manages indoor air quality (CO\textsubscript{2}) in BuildSim rooms. It was
chosen because forecasting becomes a useful component: ventilation
only affects CO\textsubscript{2} with a delay, so a plain reactive threshold is either
too late for a fast-filling room or too cautious for a slowly filling one,
while a short-horizon forecast can (in theory) give the right lead time for the
situation.

\subsection{2. Scenario}\label{scenario}

A room fills with people; CO\textsubscript{2} rises; the forecast model predicts it will
cross the threshold within the forecast horizon and the decision service
turns on ventilation early, holding CO\textsubscript{2} below the limit. When the room
empties, ventilation drops back to a low baseline. The same loop runs
independently in each room.

Each component
runs as its own container. The build stays to one sensed variable and one control
loop, rather than adding a second variable such as heating, so effort
goes into testing, evaluation, and justification rather than component
count. Whether the decision service is a single instance handling all
rooms or one instance per room, along with data storage and any
user-facing view beyond BuildSim's own, is left open for now and will be
settled once the first end-to-end loop (one room) is working.

\subsection{4. Simulating the building}\label{simulating-the-building}

CO\textsubscript{2} is modelled with a simple physics-based mass balance: concentration
rises roughly 40 ppm per occupant per hour and decays toward an outdoor
baseline at a rate set by the ventilation level. This is chosen over
replaying a fixed CO\textsubscript{2} dataset, since CO\textsubscript{2} is the variable 
the actuator controls and a pre-recorded trace cannot respond to it.

Occupancy is a separate quantity that the actuator does not affect, so it
does not carry the same constraint. It is generated from a simple
time-of-day schedule (arrivals, a meeting block, departures) with some
added randomness, rather than replaying a public occupancy dataset
(e.g.\ the UCI Occupancy Detection set) or moving individual people along
BuildSim's navigation graph. Kept simple for now so scenarios (e.g.\ a
fast-filling meeting) are easy to shape directly. The plan is to start with a
schedule + randomness; escalate to a public occupancy dataset if the
generated dynamics prove too simple to be considered realistic.

\subsection{5. The autonomous part}\label{the-autonomous-part}

The decision service compares the short-horizon CO\textsubscript{2} forecast to a fixed 
threshold and switches on ventilation before the threshold is crossed,
rather than reacting after the fact. The forecast is this project's
data-driven component and stays load-bearing in every decision.
The starting approach is to use the simplest model that produces a usable
forecast (e.g.\ exponential smoothing or a small regression over recent
readings), escalating only if it does not hold up.

\subsection{6. Biggest unknowns \& risks}\label{biggest-unknowns-risks}

\begin{itemize}
\tightlist
\item
  Whether limited experience with distributed-systems design leads to poor architectural 
  choices --- mitigated by keeping the initial design as simple as possible.
\item
  Whether a schedule-based occupancy generator produces CO\textsubscript{2} dynamics
  realistic enough for the forecast and decision to be meaningful.
\item
  Whether the simplest forecasting approach is accurate enough at this
  horizon to meaningfully outperform a plain reactive threshold, which is
  what would justify keeping a data-driven component in the loop at all.
\item
  Whether communication between the decision service and the ventilation
  actuators holds up if a call is dropped or delayed, since each
  component is an independently restartable process rather than part of
  one program.
\item
  Whether the decision service's architecture (one instance per room, or
  one instance handling several) scales cleanly to multiple rooms without
  becoming a different problem.
\end{itemize}

\subsection{7. First step \& rough plan}\label{first-step-rough-plan}

The first step is to get one room working: physical-model → sensor →
forecast service → decision service → actuator → BuildSim, feeding back into
the physical-model's next cycle, in order to prove that the loop closes and
that a ventilation change actually shows up in the next reading. Then the
loop is replicated across more rooms,
the physics/occupancy model is tuned toward believable dynamics, the
forecast model is fitted and evaluated against a plain reactive baseline,
and failure-mode testing (bad readings, a component going down, delayed
communication) is added toward the design checkpoint and the final demo.
